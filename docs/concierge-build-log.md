## Data model, member types, storefront, zones

- **Cloudflare D1** database `concierge` (NOT KV). Migrations: `/concierge-api/migrations/0001_initial.sql` — tables `members` (phone PK), `payments`, `login_attempts`. Specialties are a fixed vocabulary (**revised 2026-07-15; extended 2026-07-19**): `cabinet_construction, interior_work, solid_wood_furniture, upholstery, finishing_spray, outdoor_structures, site_construction, cnc_machining, interior_design, other` (2026-07-19 added `interior_design` only — the earlier same-day `wall_paneling/lighting/deco_supply` additions were **reverted** to keep the carpenter trade filters clean; those "what a vendor sells" items live in the vendor Storefront instead; was: furniture/glass_aluminium — legacy keys still render via fallback labels in `js/concierge.js`, rejected on save; `finishing_spray` kept deliberately — see CONCIERGE_CONTEXT.md). **Member type (`member_type`, migration 0010, 2026-07-19):** `carpenter` (default) | `vendor` — two choices at intake ("What are you?"), separate from `is_business`. Carpenters carry a skill level + trade specialties; **vendors** get a structured **Storefront** (2026-07-19). **Storefront (migration 0012):** `storefront_items` table (member_phone, name, description, free-text price, image_key, sort) — each item has one R2 image (`concierge/storefront/<phone>/<id>.jpg`, ≤300KB, reuses the member-photo compress/serve pipeline), ≤12 items/member. Vendor endpoints: `GET/POST /api/me/storefront`, `PUT/DELETE /api/me/storefront/:id`, `POST/DELETE /api/me/storefront/:id/photo`; members browse a vendor's items via `GET /api/storefront/:phone` (approved only); images at `GET /api/media/storefront/<phone>/<id>.jpg`. Vendor **shop location** = `location_lat`/`location_lng` on members (migration 0012), set via "Use my current location" (geolocation) on `PUT /api/me`, rendered as a **keyless OpenStreetMap iframe embed + a Google Maps directions link** (`mapEmbedUrl`/`mapsDirLink` in `js/concierge.js`) — avoids the deferred Maps API key. The earlier free-text `stock` column (migration 0011) is now the vendor's short **"about the shop" blurb**. Directory `.html`: a **"My Storefront" tab** (vendor-only) manages items/blurb/location; the **Sourcing tab** (previously "soon") lists vendors headlined by **company name** (`companyName` = business_name||name) → tap opens their storefront (items grid + shop map) in the member detail modal, with a WhatsApp "I'm interested in _[item]_" deep link. Deleting a member cascades storefront_items + their R2 images. **`interior_design` is a specialty available to both types and carries its own badge.** The card badge (`identityBadge` in `js/concierge.js`) resolves: interior_design specialty → gold armchair ("Interior Designer", wins); else member type → green saw (carpenter) / bronze tag (vendor). **Skill ladder (apprentice→master) shows only for carpenters; vendors instead carry a "Shop size" scale** (`vendor_scale`, migration 0013): `stall | shop | showroom | warehouse` (`VENDOR_SCALE_*`/`vendorScaleLabel` in `js/concierge.js`) — the vendor parallel to skill level, shown on their card meta + detail badge, set in register/edit/admin. Self-set at register + edit-profile, admin-settable in add/edit; directory has a type filter. The two existing vendors are re-typed by admin via the edit modal. **Vendor product categories (`vendor_categories`, JSON array, migration 0014):** what a vendor sells — `materials, hardware, tools_machinery, tooling_consumables, finishes, interior_decor, lighting, glass_alu_stone, upholstery_supplies, interior_design, other` (`VENDOR_CATEGORY_*`/`vendorCategoryLabel` in `js/concierge.js`). Vendors pick these **instead of** the carpenter trade picker (register/edit/admin swap the picker by type); `interior_design` here also fires the armchair badge (identityBadge checks specialties OR vendor_categories). The **Sourcing tab has a category filter** (area + category). **Vendor services (`vendor_services` JSON + `services_other` TEXT, migration 0016, 2026-07-19):** a SECOND vendor axis — "what you DO" (services) separate from `vendor_categories` = "what you sell" (products). Curated vocabulary (`VENDOR_SERVICES`/`VENDOR_SERVICE_*`/`vendorServiceLabel` in `js/concierge.js`): `interior_design, installation, delivery, custom_fabrication, repairs, consultation, spraying_finishing, upholstery, rental` — **capped at 5** per vendor (`VENDOR_SERVICES_MAX`), plus a free-text **`services_other`** (≤160 chars) that shows on the profile but is **NOT a filter** (this is the "curated list + Other" model the owner chose 2026-07-19; free-text-as-filter was rejected to avoid filter fragmentation). Services are a **Sourcing filter** (`srcSvcFilter`, alongside area + product category) and render as chips ("What they do") in the member detail modal. `interior_design` **moved from vendor_categories to vendor services** — it's excluded from the category picker/filter `VENDOR_CATEGORY_ORDER` (kept in `VENDOR_CATEGORY_LABELS` + server `VENDOR_CATEGORIES` vocab for legacy data) and now lives under services; `identityBadge` fires the gold armchair for interior_design in specialties OR vendor_categories OR vendor_services. Editable in register (step 3), edit-profile, and both admin **add** and **edit** forms (the Add form gained the product/service pickers 2026-07-19 — previously it had neither, forcing an add-then-edit round trip). **Specialties are carpenter-only (fixed 2026-07-19):** `validateSpecialties` now returns `'[]'` for empty (valid); the "≥1 trade" rule is enforced only when the effective `member_type` is carpenter (register/admin-create/both updates), and all frontend trade guards are member-type aware — this fixed the bug where a vendor couldn't save their profile ("please choose at least one valid specialty"). **Business/call number (`business_phone`, migration 0014):** any member's optional alternate number so they needn't expose the personal login number; `contactPhone(m)` = business_phone||phone powers every contact CTA (card WhatsApp, storefront item WhatsApp), and the detail modal shows **WhatsApp + Call** (`telLink`) using it, with the business line shown beneath. **Hide personal number (`hide_phone`, migration 0015, 2026-07-19):** a member may hide their personal (login) number from other members — since the phone doubles as the login and some tire of open reachability. Toggle in register (step 2) / edit-profile / admin add+edit; **server-enforced: can only enable when a `business_phone` exists** (else `need_business_phone` 400), so a contact channel always remains. When set, `directory()` **redacts `phone` to null** in the member-facing payload (`sanitize` still returns the real phone to self via `/api/me` and to admin) and `contactPhone` therefore resolves to `business_phone` for all CTAs. Storefront lookups now go through `contactPhone` as the handle and `getVendorStorefront` resolves a vendor by **personal OR business phone**, so hidden vendors' storefronts still load. Known minor residual: a hidden vendor's storefront **image URLs still embed the personal phone** in the R2 key (`concierge/storefront/<phone>/<id>.jpg`) — cosmetic leak only, deferred (would need an image-key alias to fully scrub). Areas use a fixed zone vocabulary (`ZONE_GROUPS` in `js/concierge.js`); column stays TEXT, constraint is frontend-only. **Expanded to town/neighbourhood level (2026-07-20, owner-directed):** the old coarse ~21-zone list (compound labels like "Circle / Adabraka", whole-region options) alienated the sizeable out-of-Accra base and buried real near-me neighbourhoods (Adabraka, Asylum Down were missing/merged). Granularity deliberately stopped at neighbourhood/town level (not street) to avoid filter fragmentation — the GPS distance layer handles finer near-me *within* a zone. **Each region sub-group keeps its bare region name (`Ashanti Region`, …) as the "elsewhere in region" catch-all, which also keeps every legacy region-level profile valid.** The GA compound splits DO orphan a few Accra profiles to legacy values (fillZoneSelect shows them with "(update to a zone)"); owner to remap via admin or members self-update. Rationale extends the earlier "large portion of our base is outside Accra" decision (see CONCIERGE_CONTEXT.md). Maps deferred (pin + Maps-app link later, no embedded tiles).

## Login-loop guard

- **Login-loop guard (2026-11-12, a member looped back to login on his phone while the same PIN worked on the owner's):** after a correct PIN, `login.html` now checks the token actually saved (`C.getToken()===data.token`) and is unexpired by the device clock (`C.tokenAlive()`). If not, it shows a message instead of redirecting: storage blocked → open the link in Chrome (not WhatsApp/Facebook in-app browser, not incognito); clock wrong → set Date & time to Automatic. Both causes are device-side; the account/server are fine in that case. **Real cause found from the member's screen recording (same day):** the button never showed "Logging in…" and the phone ended on `DNS_PROBE` for neewoodygh.com — his flaky connection dropped `js/concierge.js`, the inline script threw on `C.tokenAlive()`, and the form fell back to a native GET submit (page reload = the "loop", and it would put phone+PIN in the URL). Member-side remedy: switch Wi-Fi/mobile data, or turn off Android Private DNS if set.

## Paystack, pay-to-join, verified, support, safety

**Paystack payments (migration 0023 `payment_intents`, scaffolding built 2026-07-19; awaiting owner's keys):** owner-directed resume of the deferred payment work. Decisions: **hosted-checkout redirect · soft gate · one-time-per-period** (GHS 50/month, founders one-time GHS 100; no auto-renew v1). **Credential boundary (binding): the OWNER provisions `PAYSTACK_SECRET` as a Worker secret and holds the money; CC never sees/enters the key or moves funds** (the code references it by name only). Flow: `POST /api/pay/init` (member; server-side `/transaction/initialize` with a derived email `<phone>@members.neewoodygh.com` since members are phone-only, amount in pesewas, `reference`, `callback_url`, channels mobile_money+card) → member redirected to Paystack's hosted page → **`POST /api/pay/webhook`** (public, verified by **HMAC-SHA512** of the raw body against `PAYSTACK_SECRET`; `charge.success` → mark intent paid + upsert the existing `payments` table with `momo_ref`=reference + notify member). Everything is **guarded by `env.PAYSTACK_SECRET`** — without it, init → 503 and members see a friendly "pay via MoMo as usual" bar, so it's safe to deploy pre-keys. `GET /api/me` now returns `membership {paid, period, exempt(admin|founder), amount_due, configured}`; `membershipStatus` = admins + founders exempt, others paid iff a `payments` row exists for the current `YYYY-MM` (so manual payers grandfather automatically). Frontend: a `#membershipBar` (soft gate — a dues banner + "Pay now", never a hard block) at the top of `directory.html`; `?pay=return` polls `/api/me` for webhook confirmation. **Owner setup (to activate): create Paystack (Ghana) acct → KYC/go-live → `npx wrangler secret put PAYSTACK_SECRET` (TEST key first) → set webhook URL `https://concierge-api.neewoodygh.workers.dev/api/pay/webhook` in the Paystack dashboard → test → swap to live key.** (Secret set + first test payment verified end-to-end 2026-07-19.)

**PAY-TO-JOIN + founder-at-intake (2026-07-20, owner-directed — REVERSES the vetting gate):** the owner chose **payment auto-approves** (no manual vetting) and **pay at signup**.
